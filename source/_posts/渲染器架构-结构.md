对于一个现代渲染器是一个 CPU 和 GPU 共同协作的过程. CPU 端往往需要保证将各种资源按照一定的规则传递给 GPU, 而在 GPU 端往往通过 Shader 来实现具体的算法和效果. 对于 CPU 端, 其主体往往分为三个层面: 业务侧面, 渲染侧面 和 GPU 侧面. 这里指代的渲染侧面和业务侧面, 可以理解为实际执行渲染的模块和执行游戏逻辑的模块.
业务层负责提交渲染意图, 渲染层用于和 GPU 进行实质交互. 对于三个侧面, 分别代表三个线程(有时渲染线程和RHI也可以是一个线程, 将其分开是UE的策略):
- 业务层面: 负责提交渲染意图, 这里的渲染意图可以有若干种具体的实现, 可以将其封装为一个 RenderRequest 对象, 内部存一个当前渲染请求的类型和一个由业务线程指定具体的回调函数(UE实际上就是这么实现的, 但是其没有封装 RenderRequest 对象). 这里需要注意线程同步的时候对共享对象的访问, 此时在渲染线程中会直接拷贝一份对象中重要信息来避免对共享对象的访问. 同时在一帧当中会有很多次渲染意图的提交, 但是本质上的都是数据的更新, 之后在本帧的最后业务线程(往往是摄像机组件)会提交一次真正的渲染请求.
- 渲染层面: 渲染线程在收到渲染请求时, 此时往往是业务线程的一帧的最后一个请求. 此时渲染线程开始基于所有更新的数据来录制提交给 RHI 线程的绘制命令. 这其中基本包括
    - 构建视图数据和计算每个视图的可见性
    - 构建 PSO 数据
    - 构建, 编译, 执行渲染依赖图. 渲染依赖图执行完之后就得到了已经录制好的渲染命令
- RHI层面: 在收到渲染线程提交的渲染命令之后, 通过动态派发走进对应的API分支, 然后解析渲染命令最后向 GPU 发送绘制调用.

对于上述的三个线程, 以下称之为 Game线程, 渲染线程 和 RHI线程.

对于 GPU 端, 这里特指基于光栅化渲染关系的渲染器, 开发者至少需要实现两种 Shader: Vertex Shader 和 Pixel Shader. 
Vertex Shader: 顶点着色器主要是的功能是处理顶点属性, 并将处理完之后的顶点属性传递给下一个阶段
Pixel Shader: 像素着色器往往位于光栅化之后, 是给每一个像素上色的着色器, 这里也是主要算法实现的地方.

对于像素着色器来说, 其本质是一个数学公式(矩阵运算)通过从CPU侧面传来的数据, 再辅以基于物理的公式实现基于物理的真实感渲染. 

# Game 线程
在Game线程中, 常见的需求有三种:

## 数据更新请求
在UE中, 场景中的容器 `Actor` 想持有某种能力必须携带某个 `Component`, 而对于渲染而言, 则是 `UPrimitiveComponent`. 该组件提供向渲染器提交请求的能力. 
不同的需要渲染的物体使用不同的 `UPrimitiveComponent` 的子类, 从而提交其对应格式的数据.
例如 Game Thread 一个 Tick 结束后, 命令队列的样子
```
CommandQueue = [
    // ---- 状态更新命令(按发生顺序)----
    UpdateTransform(Actor1),        // Actor1 移动了
    UpdateTransform(Actor2),        // Actor2 移动了
    UpdateBoneMatrices(Char1),      // 角色骨骼动画更新
    UpdateMaterialParam(Mat1),      // 材质参数变化
    AddPrimitive(NewMesh),          // 新物体加入场景
    UpdateTransform(Actor3),        // Actor3 被物理推动
    UpdateParticleData(Niagara1),   // 粒子系统更新
    RemovePrimitive(OldMesh),       // 物体被销毁
    UpdateMorphTargets(Char1),      // 角色表情变化

    // ---- 渲染请求命令(最后一个)----
    RenderViewFamily(ViewFamily),   // ← 触发整帧渲染
];
```
这里的最后一个渲染请求同时还是一个同步点, 游戏线程会主动调用 `FrameEndSync::Sync();` 避免Game线程领先太多.
同时对于多个渲染请求的情况, 可以选择将其合并为一个请求. 对于多个视口的情况, 其提交的 ViewFamily 也是不同的也就是说通常情况下一个独立进程的游戏, 其只会有一个 ViewFamily. 

## 主屏幕渲染请求
在一帧中实际上会提交多种数据更新请求, 但是对于渲染线程而言不会因为每提交一次数据更新就重新渲染一次(对于延迟渲染流程而言), 而是在最后一次提交中主动发出实际的渲染命令.
虽然上述说的一直都是渲染命令, 但是在 UE 的实现中, 并没有一个 Enum 来定义若干中命令, 而是通过传入会在渲染线程中被调用的回调函数来实现的. 所谓"实际的渲染请求", 也只不过是在回调函数中调用具体渲染器的 Render 函数. 例如:
```cpp
ENQUEUE([ViewFamily, Scene = World->Scene](FRHICommandListImmediate& RHICmdList) {
    FSceneRenderer* Renderer =
        FSceneRenderer::CreateSceneRenderer(&ViewFamily, Scene);
    Renderer->Render(RHICmdList);
    delete Renderer;
});
```
[注]: `GameViewportClient` 只是 View 的组织者, 因为渲染线程只需要使用 View 的数据, 而不需要对象(直接让渲染线程取对象会有线程的竞态问题), 所以会由 `GameViewportClient` 组织相机数据. 但是其数据来源依旧来自玩家当前相机的 View 数据

## 离屏渲染请求
在实际的游戏场景中, 往往会有各种画中画的场景, 例如: 狙击镜开镜, 小地图, 透光的且映照出内部场景的窗户等等. 面对这种情况, 现代渲染器可以会选择将这个场景单独渲染成一张 RenderTarget, 最后再将 RenderTarget 独立的渲染在屏幕中.
这里说的 RenderTarget 实际上是一种离屏渲染, GPU将图形绘制到一个独立的 Image 上, 然后再贴到屏幕上, 这种情况称这张图为 RenderTarget.
而且 RenderTarget 的渲染是独立于主屏幕的, 所以可以实现以上的画中画的效果. 在 UE 中该方式对应的 Component 为 `USceneCaptureComponent`, 其并不是 `UPrimitiveComponent` 的派生类, 而是独立的.
对于这种情况, 会有一个标志`bRenderInMainRender` 
 - true: 作为主渲染视口的一部分, 其会作为一个附加 Pass 在主渲染器的流程. 通过优先级执行谁先谁后.
 - false: 独立渲染窗口, 其会先绘制所有的 `USceneCaptureComponent` 请求的画面至一个离屏的 RenderTarget 上, 然后绘制主屏幕上的场景至 BackBuffer 中, 最后在绘制 UI 时使用 Image 控件对 Render Target 进行采样

# 渲染线程
在渲染线程这一侧, 我们主要讨论 Render() 被调用时具体发生了什么, 其更能体现出渲染侧面的整体架构. 在实际的渲光栅化染器设计中, 主要需要处理两个点:
1. 材质
2. 渲染通道

首先, 为了防止多线程下的数据竞争, 渲染线程会有一个场景, UI的镜像数据用于更新渲染.
之后对于 Render 有以下几个步骤:
```cpp
void FDeferredShadingSceneRenderer::Render(FRHICommandListImmediate& RHICmdList)
{
    FRDGBuilder GraphBuilder(RHICmdList);

    InitViews(GraphBuilder);
    /**
     * 1. Copy each View in ViewFamily base info to SceneView
     * 2. Create View Uniform Buffer
     * 3. Create GBuffer from RDGBuilder
     * 4. Create Depth Buffer (SceneDepth) from RDGBuilder
     * 5. Create Velocity Texture from RDGBuilder
     * 6. for each Light create Shadow View and Shadew Depth Texture
     */

    ComputeVisibility(GraphBuilder);
    /**
     * for each SceneView
     * 1. FrustmCull
     * 2. OcclustionCull
     * 3. GetViewRelevance
     * 4. Compute Shadow Visibility by Shadow View
     */

    FMeshElementCollector Collector(GraphBuilder, Scene, Views);

    GatherDynamicMeshElements(Collector);
    /**
     * for each RenderableElementProxy call virtual function GetDynamicMeshElements
     * 1. Select LOD depend on Distance, Screen Size, FOV
     * 2. Compute LOD Transition
     * 3. Get Material Proxy
     * 4. Create MeshBatch
     * 5. Submit MeshBatch to Collector   
     */
    Collector.ProcessTasks();

    ProcessPrePassMesh(Collector);
    ProcessBasePassMesh(Collector);
    ProcessShadowMesh(Collector);
    ProcessTranslucencyMesh(Collector);
    ProcessVelocityMesh(Collector);
    ProcessCustomDepthMesh(Collector);
    /**
     * ProcessCollectedMeshes: Mesh -> FMeshDrawCommand, which RHI Thread Handle
     * for each call process():
     * 1 MeshBatch.GetMaterialProxy() and filter out unnecessary Passes
     * 2 MeshBatch.VertexFactory.GetVertexShader(PassType)
     * 3 MaterialProxy.GetPixelShader()
     * 4 Create PSO (just example from UE, PSO State depend on your RHI Setting)
     *   - VertexShader 
     *   - PixelShader
     *   - VertexInput
     *   - PrimitiveType 
     *   - BlendState
     *   - DepthStencilState
     *   - RasterizerState
     *   - RenderTargets.xxx
     * 5 Get PSO State Cache by POS, Pipeline is giant Object. we must be create form Cache file or just one time by async
     * 6 Build MeshDrawCommand info
     *   - PSO
     *   - Shader Binding: Vertex Shader, Pixel Shader
     *   - Uniform Buffer (goto 7.)
     *   - Texture (goto 7.)
     *   - Geometry (goto 8)
     * 7 Build ShaderBindings with RDG
     *   1 MeshDrawCommand.ShaderBindings.AddUniformBuffer(RHI, MaterialProxy.GetMaterial().GetUniformBuffer)
     *   2 MeshDrawCommand.ShaderBindings.AddTexture(ResourceIndex, SamplerIndex, RHI)
     *   3 MeshDrawCommand.ShaderBindings.AddUniformBuffer(PrimitiveUniformBufferIndex)
     *   4 MeshDrawCommand.ShaderBindings.AddUniformBuffer(VertexFactoryUniformBufferIndex)
     *   5 MeshDrawCommand.ShaderBindings.AddUniformBuffer(ViewUniformBufferIndex)
     * 8. Build Geometry info
     *   - Vertex Buffer
     *   - Index Buffer
     *   - Index Count
     * 9 Add MeshDrawCommand to Collector
     */

    RenderPrePass(GraphBuilder);
    RenderLumenSceneUpdate(GraphBuilder);
    RenderBasePass(GraphBuilder);
    RenderShadowDepth(GraphBuilder);
    RenderLights(GraphBuilder);
    RenderTranslucency(GraphBuilder);
    RenderPostProcessing(GraphBuilder);
    // for each View AddPass and call CallIndexed, eg:
    /**
     *   void FDeferredShadingSceneRenderer::RenderBasePass(FRDGBuilder& GraphBuilder){
     *       for (FViewInfo& View : Views){
     *           const TArray<FMeshDrawCommand>& Commands = View.BasePassMeshDrawCommands;
     *   
     *           GraphBuilder.AddPass(
     *               RDG_EVENT_NAME("BasePass"),
     *               BasePassParameters,
     *              ERDGPassFlags::Raster,
     *               [&View, &Commands](FRHICommandList& RHICmdList){
     *                   RHICmdList.SetRenderTargets({ 
     *                       View.GBufferA->GetRHI(), View.GBufferB->GetRHI(),
     *                       View.GBufferC->GetRHI(), View.GBufferD->GetRHI() 
     *                   },
     *                   View.SceneDepth->GetRHI());
     *   
     *                   for (const FMeshDrawCommand& Cmd : Commands){
     *                       RHICmdList.SetPipelineState(Cmd.PipelineState);
     *                       ApplyShaderBindings(RHICmdList, Cmd.ShaderBindings);
     *                       RHICmdList.SetVertexBuffers(Cmd.VertexBuffers);
     *                       RHICmdList.SetIndexBuffer(Cmd.IndexBuffer);
     *                       RHICmdList.DrawIndexed(Cmd.IndexCount, 1, Cmd.IndexStart, Cmd.BaseVertex);
     *                  }
     *               });
     *       }
     *  
     */

    GraphBuilder.Execute();
    /**
     * 1. Compile() 
     *   - Pass elimination
     *   - Merging
     *   - Barrier insertion
     *   - Memory aliasing
     *   - Topological sort
     * 2. Execute()
     *   - Alloc GPU Resource form RHI, like RHICmdList.CreateTexture(Tex->Desc),
     *   - Execute the Lambda registered during AddPass execution
     * 3. Release Transient Resources
     */
  
    RHICmdList.EndFrame();
}
```
其实上述的一切流程都是基于现代图形API展开的, 或者说站在现代图形API的角度理解会更自然. 以下以Vulkan为例:

现代图形API的两个核心概念是 Pipeline 和 RenderPass, 其分别代表着光栅化图形流水线和在流水线上的先后出现的资源. 即现代API将流水线和流水线上的资源解耦. 所以在渲染器的实现中往往也会将这两个对象分开处理. 其中, 
- Pipeline 本身是一个巨大且笨重的对象, 无法做到随时创建和随时使用, 所以对于 Pipeline 渲染器会提前创建好并缓存起来(甚至缓存到文件中), 在使用 Pipeline 是再查找缓存, 如果没有才会进行创建. 
- RenderPass 是在指定在某个流水线上资源的先后次序

RenderPass 和 Pipeline 并没一一对应关系. 例如: 对于一个延迟着色流程, 往往会分为两个过程: 几何Pass 和 光照Pass. 其中光照Pass 依赖于几何Pass 产生的 GBuffer. 所以这里定义一个 RenderPass 的两个 SubPass(也可以独立定义两个RenderPass然后中间插入一个屏障, 一个RenderPass 带两个 SubPass 更高效), 第一个子通道写入多个GBuffer(颜色, 法线, PBR属性), 第二个子通道使用这些GBuffer作为输入附件进行光照计算. 对于 Vulkan 来说, 即 第一个子通道输出到多个颜色附件和深度/模板附件, 第二个子通道将这些颜色附件作为输入附件最后输出颜色附件.

> [!note] 附件
> 在 Vulkan 中, 附件本质就是一张图, 颜色附件就是存有 RGBA 的图, 深度附件就是记录深度信息的图, 其本质是就是若干带有信息的矩阵.

```cpp
// 附件数量：3 张 G-Buffer + 深度 + 最终颜色输出 = 5
const uint32_t numAttachments = 5;

// ---------- 1. 附件描述 ----------
std::array<VkAttachmentDescription, numAttachments> attachments = {};

// --- G-Buffer 0: 世界空间位置 (高精度)
attachments[0].format         = VK_FORMAT_R16G16B16A16_SFLOAT;  // 或 A2B10G10R10
attachments[0].samples        = VK_SAMPLE_COUNT_1_BIT;
attachments[0].loadOp         = VK_ATTACHMENT_LOAD_OP_CLEAR;
attachments[0].storeOp        = VK_ATTACHMENT_STORE_OP_DONT_CARE;  // 光照阶段后不再需要
attachments[0].stencilLoadOp  = VK_ATTACHMENT_LOAD_OP_DONT_CARE;
attachments[0].stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;
attachments[0].initialLayout  = VK_IMAGE_LAYOUT_UNDEFINED;
attachments[0].finalLayout    = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL;

// --- G-Buffer 1: 世界空间法线 + 材质粗糙度
attachments[1].format         = VK_FORMAT_R16G16B16A16_SFLOAT;  // 法线.xyz, 粗糙度.w
attachments[1].samples        = VK_SAMPLE_COUNT_1_BIT;
attachments[1].loadOp         = VK_ATTACHMENT_LOAD_OP_CLEAR;
attachments[1].storeOp        = VK_ATTACHMENT_STORE_OP_DONT_CARE;
attachments[1].stencilLoadOp  = VK_ATTACHMENT_LOAD_OP_DONT_CARE;
attachments[1].stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;
attachments[1].initialLayout  = VK_IMAGE_LAYOUT_UNDEFINED;
attachments[1].finalLayout    = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL;

// --- G-Buffer 2: 反照率 + 金属度
attachments[2].format         = VK_FORMAT_R8G8B8A8_UNORM;       // 反照率.rgb, 金属度.a
attachments[2].samples        = VK_SAMPLE_COUNT_1_BIT;
attachments[2].loadOp         = VK_ATTACHMENT_LOAD_OP_CLEAR;
attachments[2].storeOp        = VK_ATTACHMENT_STORE_OP_DONT_CARE;
attachments[2].stencilLoadOp  = VK_ATTACHMENT_LOAD_OP_DONT_CARE;
attachments[2].stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;
attachments[2].initialLayout  = VK_IMAGE_LAYOUT_UNDEFINED;
attachments[2].finalLayout    = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL;

// --- 深度 / 模板附件
attachments[3].format         = VK_FORMAT_D32_SFLOAT_S8_UINT;   // 或 D24S8
attachments[3].samples        = VK_SAMPLE_COUNT_1_BIT;
attachments[3].loadOp         = VK_ATTACHMENT_LOAD_OP_CLEAR;
attachments[3].storeOp        = VK_ATTACHMENT_STORE_OP_DONT_CARE; // 光照阶段不需要深度
attachments[3].stencilLoadOp  = VK_ATTACHMENT_LOAD_OP_CLEAR;
attachments[3].stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;
attachments[3].initialLayout  = VK_IMAGE_LAYOUT_UNDEFINED;
attachments[3].finalLayout    = VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL;

// --- 最终输出(例如交换链图像，这里假设格式匹配)
attachments[4].format         = VK_FORMAT_B8G8R8A8_UNORM;       // 或者你的 swapchain 格式
attachments[4].samples        = VK_SAMPLE_COUNT_1_BIT;
attachments[4].loadOp         = VK_ATTACHMENT_LOAD_OP_CLEAR;    // 也可以 DONT_CARE
attachments[4].storeOp        = VK_ATTACHMENT_STORE_OP_STORE;   // 需要呈现
attachments[4].stencilLoadOp  = VK_ATTACHMENT_LOAD_OP_DONT_CARE;
attachments[4].stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;
attachments[4].initialLayout  = VK_IMAGE_LAYOUT_UNDEFINED;
attachments[4].finalLayout    = VK_IMAGE_LAYOUT_PRESENT_SRC_KHR; // 如果需要直接呈现

// ---------- 2. 子通道引用 ----------
// Subpass 0(几何阶段): 输出到 3 个 G-Buffer + 深度
VkAttachmentReference geoColorRefs[3] = {
                                                     // 片段着色器: 在 Pipeline 中指定布局
    { 0, VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL }, // 对应空间位置 layout(location = 0) out vec4 outPosition;
    { 1, VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL }, // 对应法线     layout(location = 1) out vec4 outNormal;
    { 2, VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL }  // 对应纹理坐标 layout(location = 2) out vec4 outAlbedo;
};
VkAttachmentReference geoDepthRef = { 3, VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL };

// Subpass 1(光照阶段): 输入附件引用(读取 G-Buffer)
VkAttachmentReference lightInputRefs[3] = {
                                                     // 片段着色器: 在 Pipeline 中指定布局
    { 0, VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL }, // layout(input_attachment_index=0, binding=0) uniform subpassInput inputPosition;
    { 1, VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL }, // layout(input_attachment_index=1, binding=1) uniform subpassInput inputNormal;
    { 2, VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL }  // layout(input_attachment_index=2, binding=2) uniform subpassInput inputAlbedo;
};
// 光照阶段的颜色输出(只有最终画面)
// layout(location = 0) out vec4 outColor;: 在 Pipeline 中指定布局
VkAttachmentReference lightColorRef = { 4, VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL };

// ---------- 3. 子通道描述 ----------
VkSubpassDescription subpasses[2] = {};

subpasses[0].pipelineBindPoint       = VK_PIPELINE_BIND_POINT_GRAPHICS;
subpasses[0].colorAttachmentCount    = 3;
subpasses[0].pColorAttachments       = geoColorRefs;
subpasses[0].pDepthStencilAttachment = &geoDepthRef;

subpasses[1].pipelineBindPoint       = VK_PIPELINE_BIND_POINT_GRAPHICS;
subpasses[1].inputAttachmentCount    = 3;                    // 读取 3 张 G-Buffer
subpasses[1].pInputAttachments       = lightInputRefs;
subpasses[1].colorAttachmentCount    = 1;
subpasses[1].pColorAttachments       = &lightColorRef;

// ---------- 4. 子通道依赖 ----------
std::array<VkSubpassDependency, 2> dependencies = {};

// 依赖 1: 几何阶段完成 → 光照阶段开始(确保 G-Buffer 写入可见)
dependencies[0].srcSubpass      = 0;
dependencies[0].dstSubpass      = 1;
dependencies[0].srcStageMask    = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT;
dependencies[0].dstStageMask    = VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT;
dependencies[0].srcAccessMask   = VK_ACCESS_COLOR_ATTACHMENT_WRITE_BIT;
dependencies[0].dstAccessMask   = VK_ACCESS_INPUT_ATTACHMENT_READ_BIT;
dependencies[0].dependencyFlags = VK_DEPENDENCY_BY_REGION_BIT;  // 允许 tile 级并行

// 依赖 2: 上一帧的最终输出 → 本帧的最终输出(可选，如果帧缓冲复用)
dependencies[1].srcSubpass      = VK_SUBPASS_EXTERNAL;
dependencies[1].dstSubpass      = 0;
dependencies[1].srcStageMask    = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT;
dependencies[1].dstStageMask    = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT;
dependencies[1].srcAccessMask   = 0;
dependencies[1].dstAccessMask   = VK_ACCESS_COLOR_ATTACHMENT_WRITE_BIT;

// ---------- 5. 创建 Render Pass ----------
VkRenderPassCreateInfo renderPassInfo = {};
renderPassInfo.sType           = VK_STRUCTURE_TYPE_RENDER_PASS_CREATE_INFO;
renderPassInfo.attachmentCount = numAttachments;
renderPassInfo.pAttachments    = attachments.data();
renderPassInfo.subpassCount    = 2;
renderPassInfo.pSubpasses      = subpasses;
renderPassInfo.dependencyCount = static_cast<uint32_t>(dependencies.size());
renderPassInfo.pDependencies   = dependencies.data();

VkRenderPass renderPass;
vkCreateRenderPass(device, &renderPassInfo, nullptr, &renderPass);
```
上述 RenderPass 的创建中创建了对应的 GBuffer, 其在 Pipeline 中的具体位置在 `VkDescriptorSetLayoutCreateInfo` 中设置. 同样地, 更复杂的场景也会使用到更复杂的 RenderPass 和 Pipeline 之间的对应关系. 
而现代渲染器流程正是在 CPU 端区别了 RenderPass 和 Pipeline 这两个流程. 其主要实现方式是渲染依赖图 RDG(见具体章节). 

# RHI 线程
正如之前所言, RHI 单独开一个线程并不是必须的. 但是如果像 UE 一样选择开一个新的线程, RHI 线程的功能是将渲染线程录制的命令转义为 GPU 能识别的格式, 其核心是将各个平台的 API 的用统一种接口进行分发. 从而实现跨平台.
